## 3. 저장 구조 — 확인된 것

### 3.1 `TEXT2.BIN` (확정)

`BATLE/TEXT2.BIN` 20,940 B, `FIELD/TEXT2.BIN` 26,192 B. 둘 다 같은 헤더로 시작.

- 앞머리 = **BE32 오프셋 테이블**, 오름차순이며 전부 파일 범위 안:
  `0x2C, 0xB8, 0x428, 0xB68, 0xDBC, 0x1104, 0x1764, 0x2184, …`
- 본문 = **1바이트 반각 가타카나(JIS X0201)** + `0x00` 구분자.
  예: `C3 DE CC DB BD` = ﾃﾞﾌﾛｽ(デフロス), `B8 DE D7 B7 DE DD` = ｸﾞﾗｷﾞﾝ
- 즉 이름 목록류(캐릭터·몬스터·아이템 후보)

멀티바이트가 아니라 **1바이트 인코딩**이라는 점이 한글화 설계에 결정적이다.

### 3.2 `.STB` (후보)

`BATLE/SYS_B.STB` 18,542 B, `FIELD/SYS_F.STB` 26,342 B, `BIN/SYS_T.STB` 153,502 B,
그리고 `FIELD/MG*_1.STB`, `SD8__.STB`, `SE*__.STB` 등.

- 앞머리 = BE32 오프셋 테이블(오름차순, 파일 범위 내). 첫 값 `0x200`, 둘째 `0x234`
- `0x234`에 ASCII 매직 **`ST1`**
- `SYS_F.STB`와 `SYS_T.STB`는 헤더 24바이트가 완전히 동일

**미확정**: 대사 스크립트인지, 3D/모션 데이터인지. `ST1` 이후 구조 미해독.

### 3.3 `MES1B.DAT` / `MES1C.DAT` (후보)

앞머리 32 B가 BE16 16개의 균등 증가열(`0x0000, 0x0842, 0x1084, … 0x77BD, 0x7FFF`)
= **RGB555 16색 그레이스케일 팔레트**. 이어지는 데이터는 `0x0800, 0x0801, 0x0802…`
같은 증가 BE16 열 → **VDP2 패턴 네임 테이블(타일맵)** 형태.
즉 "메시지 화면을 타일로 찍은 그래픽" 후보.

### 3.4 `EDFNT.DAT` — 이름과 달리 폰트가 **아니다** (확정)

`BIN/EDFNT.DAT`와 `FIELD/EDFNT.DAT` 각 284,964 B (두 파일은 **서로 다름**).

- 앞머리 500 B = **BE32 섹션 오프셋 125개**, 첫 섹션 `0x1F4`
- 섹션 크기는 모두 288의 배수 (576, 4608, 4320, 1440, 2016, …)
- 엔트로피 1.46~4.06 bit/B → **비압축**
- 실측 stride 192 B(자기상관 0.903, 기대치 0.648 대비 뚜렷한 단봉)
- 형식 = **4bpp 선형(타일 인터리브 아님), 폭 = 24 × 글자수, 높이 24**

섹션 1(0x434, 4608 B = 384×24)을 렌더하니 「ジャスティン　瀧本 富士子」
(캐릭터명 + 성우명)가 나왔다. → **엔딩 크레딧을 통째로 구운 비트맵 텍스트**,
125줄. 폰트가 아니라 그래픽 텍스트 모집단이다.

한글화하려면 같은 규격(24×24 4bpp, 폭 24×N, 선형)으로 **다시 그려 넣으면** 된다.
글리프 인코딩이 개입하지 않으므로 난이도는 낮은 편이나, 줄 폭이 바뀌면
섹션 크기가 바뀌어 오프셋 테이블 재계산이 필요하다.

## 3.5 폰트 탐색 (세션 1 후반) — **아직 미발견**

### 탈락시킨 후보 (확정)

| 후보 | 판정 근거 |
|------|-----------|
| `EDFNT.DAT` | 구운 크레딧 비트맵 (§3.4) |
| `SWN5M/5B, SWN6M/6B, SWN9M/9B.DAT` | stride 자기상관이 **4 B**에서 단조 감소 → 넓은 비트맵이 아니라 4바이트 레코드열. VDP2 패턴 네임(타일맵) 형태 |
| `WIN5/WIN9/MWIN6/WINBK.BIN` | 선두가 **SH-2 절대주소**(`0x0602C018`, `0x060B2038` = Work RAM High) → 압축 자산이 아니라 **로더블 모듈**. 렌더하면 기계어 잡음 |
| `B*.BBG` 섹션#0 내 `0x11BD1-0x164DB` | 비영 99.5%·stride 단봉 없음 → 밀집 이미지. 영문패치 체인지로그의 "Battle Menu Text"와 일치하는 **전투 UI 그래픽** |

### 코드 색인 지문 스캔 = 0건 (확정)

`TEXT2.BIN`이 1바이트 JIS X0201을 쓰므로, 코드값으로 색인되는 글리프 시트가
있다면 `0x20`·`0x7F-0xA0`·`0xE0-0xFF`가 비고 `0x21-0x7E`·`0xA1-0xDF`만
채워져야 한다. 셀 8/12/16/24/32/72/128 B로 2 MB 이하 전 파일을 훑어 **0건**
(`tools/scan_x0201.py`).

→ 폰트는 (a) 압축돼 있거나, (b) `GM3.STZ`(248 MB) 등 대용량 컨테이너 안이거나,
(c) 코드 색인이 아닌 재배치 테이블을 거치거나, (d) 2바이트 색인 한자 폰트다.

### 영문패치 차분 포맷 해독 (확정) — `tools/bsdiff_map.py`

`_DFR` = **BSDIFF40 + bzip2** 표준 포맷. 헤더 `"BSDIFF40"` + ctrl/diff 길이 +
새 크기, 이어서 bzip2 스트림 3개(ctrl/diff/extra). 제어 항목 `(x, y, z)`를
따라가면 **원본(일본판 본편)이 없어도 "새 파일에서 바뀐 구간"** 을 뽑을 수 있다.

이걸로 얻은 본편 변경 지도의 요점:

- 루트 파일 `0` — 본편에서 **486,736 B**이고 영문패치가 **474,316 B(≈97%)** 를 갈아엎었다.
  즉 본편의 `0`은 **메인 프로그램**이다.
  그런데 **DM의 `0`은 11,908 B**뿐이고 내용도 `0x0600xxxx` 주소 나열이다.
  → DM은 프로그램 구성이 다르며, 본편 `0`의 폰트 위치를 DM에 이식할 수 없다.
- `B*.BBG`는 **전 파일이 완전히 같은 오프셋**(`0x11BD1-0x164DB` 등)에서 바뀌었다
  → 전투 UI 그래픽이 배경마다 복제돼 있다. DM도 같은 복제 구조인지는 미확인
  (DM의 BBG끼리는 같은 오프셋에 공통 구간이 없었다).

**주의**: 본편과 DM은 파일 배치가 실제로 다르다. 영문패치의 오프셋을 DM에
그대로 대입하면 안 된다.

## 3.6 세이브스테이트 오라클 (세션 1 말) — 폰트 여전히 미발견

입력: `D:\hospi\RetroArch\states\Beetle Saturn\Grandia - Digital Museum (Japan) (Rev A) (10M).state`

### 포맷 해독 (확정)

- 바깥 = RetroArch **RZIP** (`"#RZIPv\x01#"` + 청크크기 LE32 + 전체크기 LE64 +
  `[LE32 압축길이][zlib]` 반복). 푼 크기 6,845,568 B → `tools/rzip.py`
- 안쪽 = Mednafen 세이브스테이트. 변수 레코드 = `[u8 이름길이][이름][u32 LE 크기][데이터]`
  → `tools/parse_state.py`

꺼낸 메모리 블록:

| 이름 | 크기 | 내용 |
|------|------|------|

| `&FB[0][0]`, `&AltFB[0][0]` | 524,288 | VDP1 프레임버퍼 (이번 스테이트에서는 **비어 있음** → 스프라이트 레이어 미사용 화면) |

### 시도했고 실패한 것 (기록해 반복 방지)

1bpp 글리프 런 탐색(셀 8/12/16/24/32 B)과 4bpp 글리프 런 탐색(8x8/12x12/16x16/12x16/24x24)을
`WorkRAML`·`WorkRAMH`·VDP1/VDP2 VRAM 전체에 적용해 상위 후보를 전부 렌더했으나
**글자로 보이는 것은 없었다**. VDP2 VRAM 하단에 규칙적인 구조가 있으나
1bpp·4bpp 어느 쪽으로도 세로 줄무늬만 나온다(비트depth 또는 뱅크 인터리브 미확정).

### 대사 2장 차분 (수행함)

`state_a`(대사 A) ↔ `state_b`(다음 대사)를 차분한 결과:

| 영역 | 다른 바이트 |
|------|-------------|
| VDP2 VRAM | 3,665 / 524,288 (0.70%) |
| VDP1 VRAM | 2,381 / 524,288 (0.45%) |
| Work RAM H | 2,833 / 1,048,576 (0.27%) |
| Work RAM L | 1,727 / 1,048,576 (0.16%) |
| CRAM | **0** |

VDP2 VRAM 최대 변경 구간 `0x00400E-0x004EFA`(3,820 B), 그 외 `0x8000-0x847A`.
`0x8000`대는 니블이 0과 F만 쓰는 고대비 4bpp였고, `0x4000`대는 고유값 48종이다.
두 구간 모두 렌더했으나 **완전한 글자 형태로 읽히지 않았다**(획 조각만 보임).

### ★ 선행 프로젝트에서 얻은 교정 (중요)

`C:\claude\project\shining-kr-patch\docs\03_dynamic_vram.md`에 이미 있던 사실:

1. **세이브스테이트의 Work RAM은 16비트 바이트스왑되어 저장된다.**
   → 이번 세션의 Work RAM 스캔은 전부 스왑 없이 돌려 **원천적으로 매치될 수 없었다**.
   `tools/map_loaded.py`가 스왑본을 쓰도록 고쳤다.
2. **이 계열 엔진은 폰트 타일 인덱스를 쓰지 않는다.** 1bpp 글리프 테이블을 RAM에
   상주시키고, 렌더러가 색을 입혀 스테이징 버퍼를 거쳐 VRAM에 **블릿**한다.
   → 글리프 원본은 **대사가 바뀌어도 변하지 않으므로 차분에 절대 잡히지 않는다.**
   차분으로 얻은 것은 블릿 *결과*이지 폰트가 아니다.
3. Shining의 폰트 엔트리 형식(참고용, 이식 금지): 32 B = `[폭 2B BE] + 15행 × 2B BE 1bpp`.
   파일 `DEBUG.FNT`가 고정 주소로 적재됐고, **파일→로드주소 표**를 만들어 찾아냈다.

→ 따라서 Grandia DM에서도 **파일→로드주소 대응표**를 만드는 것이 정공법이다.
블릿 결과에서 1bpp 원본을 역검색하는 시도(`tools/find_glyph_src.py`)는 0건이었는데,
블릿 구간을 잘못 골랐을 가능성이 크다(§위 두 구간 모두 글자로 안 읽힘).

| 그 외 `.BIN` 모듈 약 35개 | WRAM H `0x0600xxxx` | |

`FIELD.BIN`의 적재주소 `0x0602C000`은 파일 헤더의 `0x0602C018`과 일치한다
→ **`.BIN` 선두가 적재주소**라는 §3 결론이 독립 증거로 교차 검증됐다.

## 3.8 폰트 — 여전히 미발견 (탈락 후보 추가)

`tools/uncovered.py` — 디스크 섹터와 매치되지 않는 상주 구간(=런타임 생성 또는

가장 유력해 보였던 두 블록을 렌더해 탈락시켰다:

| `WorkRAML_sw 0x090000` (버스 `0x00290000`) | 6,144 B (= 12×12 1bpp × 256개와 정확히 일치) | **비트밀도가 너무 높다(대부분 채움) → 압축/3D 데이터. 폰트 아님** |

### 다음 수순 (권장) — 블라인드 스캔 중단, 렌더러 역공학

줄이는 데는 기여했지만 폰트를 짚어내지 못했다.

## 3.9 렌더러 역공학 착수 (세션 1 말)

디스어셈블 코어는 기존 자산 재사용: `terra-kr-patch/tools/sh2_disasm.py`를
`shining-kr-patch/tools/disasm.py`가 감싼다. `FIELD.BIN`을 적재주소
`0x0602C000` 기준으로 디스어셈블한다.

### 리터럴 스캔 (`tools/scan_literals.py`)

⚠️ **하위 27비트만 보고 주소를 판정하면 안 된다.** SH-2 명령어 워드가 대량으로
주소처럼 보인다(예: `0x65E3430B` = `mov r14,r5` + `jsr @r3`). 상위 니블이
캐시(`0x0`)/비캐시(`0x2`) 별칭인 값만 인정하도록 고쳐야 거짓양성이 사라진다.

`FIELD.BIN`의 진짜 주소 리터럴: VDP2_VRAM 66개, VDP1_VRAM 29개, CRAM 17개,
VDP1_reg 5개, WRAM_Hi 6,172개, WRAM_Lo 471개.

### ★ 텍스트 전송 디스패처 확정 (버스 `0x06042420`~`0x06042464`)

```
06042420: MOV.L @(PC+244),R6   => 0x25F00640  VDP2_CRAM
06042434: MOV.L @(PC+232),R6   => 0x25E04000  VDP2_VRAM   ← 대사가 바뀐 바로 그 위치
0604243C: MOV.L @(PC+220),R6   => 0x25F00600  VDP2_CRAM
06042440: MOV.L @R13,R5
06042442: JSR @R14
06042444: MOV #0x04,R4
...
0604244C: JSR @R14
0604244E: MOV #0x07,R4
```

= `R14(R4=종류, R5=원본, R6=목적지, R7=0)` 형태의 **전송 루틴 호출**이며,
목적지가 대사 차분으로 확인된 VDP2 VRAM `+0x4000`과 팔레트 CRAM이다.
원본 `R5`는 `@R13` / `@R12`(포인터 변수)에서 온다.

**→ 다음 수순: `R14`의 실체와 `R12`/`R13`이 가리키는 원본 버퍼를 따라가면
폰트(또는 글리프 소스)에 도달한다.** 이것이 남은 최단 경로다.

부수 확인: 같은 함수가 `0x06072E60`을 참조하는데, 이 주소는 4bpp 글리프 스캔과
"출처 없는 상주 구간" 목록에도 걸렸다. 다만 렌더 결과는 글자가 아니라
데이터 테이블이었다(플래그 바이트를 쓰는 코드와 일치). **폰트 아님.**

## 3.10 ★ 블릿 목적지·스테이징 버퍼 확정 (사용자 화면 확인)

`work/f_sw_8x16.png`를 사용자가 확인해 준 결과, 화면의 대사
「フィーナ！ スー！ / あ あれ！？」가 그대로 읽혔다.

**확정 1 — VDP2 VRAM도 swap16 저장이다.** (Shining 문서에서는 "미확정"이던 항목)
스왑하지 않은 VDP2 VRAM으로는 어떤 렌더도 글자로 읽히지 않는다.

**확정 2 — 블릿 목적지 = VDP2 VRAM(스왑본) `0x8000`부터,
8px 폭 × 16행 4bpp 셀(64 B)이 연속.** 셀 2개가 가로로 이어져 16px 글자를 이룬다.

**확정 3 — Work RAM에 같은 4bpp 셀이 존재한다(스테이징/글리프 캐시).**
블릿 셀 8·9의 64 B가 `WorkRAMH_sw + 0x020070`, `+0x0200B0`에 **바이트 그대로**
있다(간격 0x40 = 셀 1개). 버스 `0x06020070`.
대사 A↔B 차분의 변경구간 `0x020039-0x020052`, `0x020074-0x0200E9`와 정확히 일치한다.

### 여기서 얻은 부정 결론 (중요)

블릿 결과를 1bpp로 환원해 RAM 전체에서 역검색했으나 **0건**이다
(정방향·비트반전·앞 8행만, 스왑/비스왑 RAM 모두). 즉 **폰트는 화면과 같은 모양의
1bpp 비트맵으로 RAM에 놓여 있지 않다.** 글리프는 이미 4bpp 형태로 캐시에 있다.

→ 폰트 원본은 (a) 디스크에서 압축 저장돼 4bpp로 해제되거나,
(b) 다른 인코딩(런렝스·가변폭)으로 저장돼 전개되는 것이다.

### 다음 수순

`0x06020000`대를 리터럴로 들고 있는 모듈은 없다(계산 주소).
포인터 변수 역추적도 시도했으나 **거짓양성만 나왔다**: 값 `0x0602000C`·`0x0602000E`
등은 포인터가 아니라 SH-2 명령어 워드다(`0x0602` = `MOV.B @(R0,R0),R6`,
`0x000C` = `MOV.B @(R0,R0),R0`). 참조 코드 0건.

⚠️ **이 세션에서 같은 함정에 세 번 빠졌다.** 32비트 값이 주소 범위에 든다는 이유만으로
주소로 판정하면 안 된다. 최소한 (a) 상위 니블이 `0x0`/`0x2`, (b) 정렬 조건,
(c) 주변 워드가 리터럴 풀답게 보이는지를 함께 요구해야 한다.
관련 메모리: 대용량 바이너리 스캔의 노이즈 함정.

**다음 세션 착수점**: 스테이징 버퍼 `0x06020070`에 **쓰는** 코드를 찾는다.
리터럴 검색이 막혔으므로, 정공법은 `FIELD.BIN`(적재 `0x0602C000`)에서
VDP2 VRAM `0x25E08000`(블릿 목적지)을 참조하는 지점을 찾아 역방향으로 호출자를
따라가는 것이다. `tools/scan_literals.py`의 엄격 필터 결과(`work/literals.txt`)에
`0x25E07000`·`0x25E10000` 등이 이미 나와 있으니 그 주변부터 본다.

## 3.11 확정된 글자 모양으로 디스크 전수 검색 — 전부 음성 (중요)

사용자 확인된 화면 글자(「フィーナ！ スー！ / あ あれ！？」)를 기준으로
질의를 만들어 **Track 1 전체 455 MB**와 RAM 전 영역을 검색했다.
도구: `tools/find_font_on_disc.py`, `tools/find_font_core.py`.

글리프 비트패턴은 정상적으로 추출된다. 예(16px, 2바이트/행):

| 글자 | 핵심 행 |
|------|---------|
| `ナ` | `0180 0180 0180 0180 7ffc 0180 …` |
| `フ` | `7ffc 000c 000c 000c 000c 000c …` |

시도한 저장 형태와 결과:

| 질의 형태 | 디스크 | RAM |
|-----------|--------|-----|
| 4bpp 원본 64 B / 32 B | 잡음 1건 | 캐시(`0x06020070`)에만 존재 |
| 1bpp 16행 × 1 B (8px) | 없음 | 없음 |
| 1bpp 16행 × 2 B (16px), 워드스왑 포함 | 없음 | 없음 |
| 비트 반전 | 잡음 2건(`GM3.STZ`, 0이 많은 패턴) | 없음 |
| **앞뒤 빈 행 제거한 핵심 행**(헤더·높이 차이에 둔감) | **0건** | **0건** |

→ **폰트는 디스크에 비압축 비트맵으로 존재하지 않는다.** RAM에도 1bpp 형태가
없고 오직 4bpp 캐시만 있다. 즉 **압축 저장 → 글리프 단위로 4bpp로 직접 해제**된다.

### 텍스트 인코딩도 표준이 아니다

화면에 히라가나(`あ`)가 있으므로 반각 가타카나가 아니다. 그런데 대사 문자열을
**Shift-JIS(cp932)와 EUC-JP 양쪽**으로 인코딩해 디스크·RAM 전체를 검색한 결과
`フィーナ` `スー` `あれ` `ジャスティン` `ですか` `ました` **전부 0건**이다.

→ 대사는 **자체 문자 코드**를 쓴다(`TEXT2.BIN`의 1바이트 가타카나와 같은 계열의
독자 코드일 가능성이 높다).

### 결론 — 남은 경로는 코드뿐

폰트도 텍스트도 표준 형식이 아니므로 **패턴 검색으로는 더 진전할 수 없다.**
글리프 압축 해제 루틴을 찾아 읽는 것만 남았다. 착수점은 확정돼 있다:
글리프 캐시 `0x06020070`에 쓰는 코드.

## 4.2 ★ 폰트가 존재한다는 직접 증거 (확정, 신규)

한 줄 안에서 **같은 글자끼리 비트가 완전히 동일**하다.

- 상자 2 ≡ 상자 7 (`ー`)
- 상자 4 ≡ 상자 8 (`！`)
- 상자 10 ≡ 상자 12 (`あ`)

→ 줄 전체를 구운 비트맵이 아니라 **글리프를 색인해 재사용**하는 폰트 렌더링이다.
(`EDFNT.DAT`처럼 구운 텍스트일 가능성은 이로써 배제된다.)

## 4.3 스테이징 버퍼 재확인 (세션1 "확정 3" 유지)

`work/cells_WRH_20070.png` — `WorkRAMH_sw + 0x020070`을 4bpp 8×16 셀로 렌더하면
**「！」 한 글자가 정확히 2셀**로 있고 주변은 비어 있다.
셀 8은 비영 바이트가 19/64로 우연일치로 보기 어렵고, 두 셀은 0x40 간격으로 인접한다.
→ **글자 단위(128 B) 스테이징 버퍼가 맞다.**

## 4.4 부정 결과 — 각각이 큰 탐색 공간을 닫는다

### (a) stride 무제한 2차원 글리프 검색 = 0건 (`tools/find_font_stride.py`)

세션1까지의 검색은 전부 "글리프 16행이 **연속** 저장"을 가정했다.
그러나 이 엔진은 `EDFNT.DAT`에서 보듯 텍스트 비트맵을 **선형 시트**로 저장하므로,
폰트가 시트라면 한 글자의 각 행은 시트 폭만큼 떨어져 있어 연속 검색은 원리상 실패한다.

그래서 **행 간격 S를 미지수로 둔 2차원 검색**을 구현했다.
인접한 두 비영 행을 앵커로 잡아 이분탐색으로 S 후보를 만들고 전 행을 검증한다.

- 대상: 디스크 Track1 **사용자 데이터만 이어붙인 396,533,760 B 이미지**
  (raw 2352 섹터에서 검색하면 304 B 여백이 패턴을 끊는다) + 세이브스테이트 RAM 전 영역
- 질의 96개 = 잉크 있는 상자 12개 × {원본, 오른쪽볼드제거, 왼쪽볼드제거}
  × {바이트순 정상/스왑} × {비트순 정상/역순}
- 허용 stride 1~65536
- **결과 0건**

### (b) 구조적 폰트 표 검출 = 없음 (`tools/detect_font_region.py`, `tools/font_runs.py`)

글리프 모양 복원이 틀렸을 가능성에 대비해, **모양을 전혀 쓰지 않는** 검출기를 만들었다.
1bpp CJK 폰트 표의 구조 지문(글자마다 첫 행·끝 행이 빔, 잉크 밀도 8~45%,
미사용 코드의 빈칸이 섞임)만 본다. 글자칸 8/16/24/32/48/72/128 B.

- 대상: 4 KB 이상 **디스크 전 파일** + 세이브스테이트 RAM 전 영역
- 단발 히트는 잡음이므로 **96글자 이상 연속**만 인정
- 상위 후보는 `GM3.STZ`의 72 B 구간 3곳(6945·6056·3499글자)뿐이었고,
  렌더해 보니 **규칙적인 스트림 데이터**였다 (`work/gm3_a.png`) — 폰트 아님
- 나머지는 `.BBG`/`MGDAT.BIN`의 179글자 이하 짧은 구간 = 잡음

### (c) 스테이징 버퍼 주소를 든 자리 = 0건 (`tools/find_stage_ptr.py`)

`0x06020000`~`0x060200FF` 범위의 BE32 값을 캐시/비캐시/DMA 별칭까지 포함해
전 RAM·전 모듈에서 찾았다. **Work RAM에는 한 건도 없다**
(VDP1 VRAM·CD 버퍼의 히트는 명령 리스트 잡음).
→ 버퍼 주소는 리터럴도 포인터 변수도 아닌 **계산 결과**다. 세션1 판정과 일치.

### (d) 1bpp→4bpp 비트확장 룩업표 = 0건 (`tools/find_spread_table.py`)

2/4/8비트 확장표를 색 인덱스 1~15 × 니블 순서 2종 = 60종으로 만들어
전 RAM·전 모듈에서 찾았다. **0건** → 확장은 표가 아니라 시프트 연산으로 한다.

## 4.5 종합 판정

> 디스크 어디에도, RAM 어디에도 **평문 1bpp 폰트는 없다.**
> 그런데 글리프 색인 렌더링은 확실히 일어난다(4.2).
> 세이브스테이트 시점에 그 글자의 사본은 **스테이징 버퍼와 VDP2 VRAM 두 곳뿐**이다.
>
> → 폰트는 **압축 또는 비(非)비트맵 부호화**로 상주하며,
>   **글자 단위로 곧장 4bpp 스테이징 버퍼에 전개**된다. 중간 1bpp 사본이 없다.

## 4.6 `GM3.IDX` 해독 (확정, 신규)

`FIELD/GM3.IDX` 4,096 B = **`[BE16 A][BE16 섹터오프셋] × 1024`**, 꼬리는 `FFFFFFFF` 패딩.

- 유효 레코드 **369개**
- 섹터오프셋은 16비트라 **정확히 1회 랩**한다 → 복원하면 0 ~ 120,885
- `GM3.STZ` = 248,184,832 B = **121,184 섹터** → 마지막 청크 299섹터로 딱 맞는다
- 청크 크기 20~4,551섹터(40 KB~9.3 MB), 최빈 31~32섹터(64 KB)·80~81섹터(164 KB)
- 필드 A는 미해독 (ID 후보, 상위 비트가 플래그로 보임)

도구 `tools/stz_survey.py` — 369청크의 경계와 머리 32 B를 훑는다.
**248 MB 컨테이너의 경계가 확보됐다**는 점이 이번 세션의 부수 성과다.

# ★ 5. 폰트 발견·해독 (세션 2, 확정)

동적 분석(에뮬레이터 디버거)으로 대사 출력 직전에 멈춰 얻은 PC 근방을
세이브스테이트에서 디스어셈블해 **글리프 전개 루틴 전체를 해독**했다.

## 5.1 폰트 파일

**`/BIN/FDATA.BIN` (64,348 B, 적재 주소 `0x00200000` = Work RAM Low)**

세션1이 "BE16 표 128항목, 평균 14.6 B → 데이터 테이블"이라며 탈락시킨 파일이다.
그 128항목이 **반각 오프셋표**였고, 14.6 B가 **XOR 델타 압축된 글리프 크기**였다.

| 폰트 | 베이스 | 오프셋표 | 글자 수 | 데이터 끝 |
|------|--------|----------|---------|-----------|
| 반각 8×16 | `FDATA+0x000` (버스 `0x00200000`) | BE16 × 128 | 128항목 × 2코드 = **256** | `0x842` |
| 전각 16×16 | `FDATA+0xA00` (버스 `0x00200A00`) | BE16 × 1504 | **1,504** | `0xA681` |

`0xA681`~`0xAA02`는 0 패딩, `0xAA03` 이후 21 KB는 폰트가 아닌 별개 데이터
(런타임에는 이 구간이 다른 데이터로 덮인다 — 세션1의 "출처 없는 상주 구간
`0x0020AA03-0x0020C000`"과 일치).

폰트 베이스는 **포인터 변수**로 주어진다.

- `*(0x06021D24)` = `0x00200A00` (전각)
- `*(0x06021D20)` = `0x00200000` (반각)
- `*(0x06021CF0)` = 모드 플래그(0이면 전각 경로), `*(0x06021CF1)` = **색 바이트 `0xF0`**
  (비트1 → 상위니블 15 = 전경, 비트0 → 하위니블 0 = 배경. 관측된 0/15와 정확히 일치)

## 5.2 ★ 코덱 — 세로 XOR 델타 (확정)

**이것이 모든 평문 검색이 0건이었던 이유다.**

```
레코드 = [BE32 플래그워드][델타바이트 × popcount(플래그워드)]
```

- 글리프는 32바이트 = **왼쪽 8px 열 16행(바이트 0~15) + 오른쪽 8px 열 16행(16~31)**
- 플래그워드를 **MSB부터** 한 비트씩 소비하며 32바이트를 만든다
  - 비트 1 → 델타를 하나 읽어 누산기에 **XOR**
  - 비트 0 → **이전 값 그대로** (그 행은 윗행과 동일)
- 누산기는 **바이트 0과 16에서 0으로 리셋** (좌·우 열이 각각 독립 체인)

즉 세로로 이웃한 행끼리의 차분만 저장한다. 한자처럼 세로획이 긴 글자는
같은 바이트가 반복되므로 플래그 0이 길게 이어져 크게 줄어든다.

## 5.3 전개 루틴 (Work RAM High 상주 코드)

| 주소 | 역할 |
|------|------|
| `0x0601DC00` | **글리프 전개 진입점** — `R4` = 목적지(스테이징 버퍼), `R5` = 글자 코드 |
| `0x0601DC7C` | 반각 경로 (코드 `&0xFFFE`로 색인, 코드 홀수면 앞 16바이트 델타를 popcount로 건너뜀) |
| `0x0601DC20` | 전각 경로 (`R11=7`, `R9=15` → 16회 × 2바이트 = 32바이트) |
| `0x0601DD56` | **1bpp 1바이트 → 4bpp 32비트 확장** (색 바이트의 상위/하위 니블 선택) |
| `0x0601DDF8` | popcount (반각 홀수 코드에서 델타 건너뛰기용) |

색인 코드(어셈블리 그대로):

```
0601DC24: MOV.L @R2, R13        ; R13 = *(0x06021D24) = 폰트 베이스
0601DC28: SHLL  R0              ; R0 = 코드 * 2
0601DC2A: MOV.W @(R0,R13), R5   ; R5 = BE16 오프셋            ← 0x05DD
0601DC2E: ADD   R5, R13         ; R13 = 베이스 + 오프셋
0601DC32~48:                    ; R14 = BE32 플래그워드
0601DCD4: MOV.B @R13+, R3       ; 델타 바이트
0601DCD8: XOR   R3, R8          ; ★ 누산기에 XOR
0601DCDA: SHLL  R14             ; 플래그 다음 비트로
0601DCDC: BSR   0x0601DD56      ; 4bpp 확장
0601DCF8: MOV.L R4, @R12        ; 스테이징 버퍼에 기록, R12 += 4
```

## 5.4 검증 — 바이트 전체 대조 (통과)

`tools/font_decode.py`로 디코드한 글리프를, 세이브스테이트 VDP2 VRAM에서 뜯은
화면 글리프와 **전체 대조**했다(스캔 아님 — [[feedback_terra_verify_by_render_not_scan]]).

**잉크 있는 12상자 전부, 0~14행이 바이트 단위로 완전 일치.**
(15행만 다른데, 화면 쪽 마지막 행이 캡처 시점에 안 찍혀 있었기 때문이다.)

| 상자 | 0 | 1 | 2 | 3 | 4 | 6 | 7 | 8 | 10 | 12 | 13 | 14 |
|------|---|---|---|---|---|---|---|---|----|----|----|----|
| 글자 | フ | ィ | ー | ナ | ！ | ス | ー | ！ | あ | あ | れ | ？ |
| 코드 | 0AA | 078 | 0CF | 09F | 0CD | 08E | 0CF | 0CD | 026 | 026 | 070 | 0D7 |

같은 글자가 같은 코드로 나오고, 세션 2 §4.2에서 "비트 동일"로 관측한 쌍
(2≡7, 4≡8, 10≡12)과 정확히 일치한다.

## 5.5 문자 인코딩 (부분 확정)

대사는 SJIS도 EUC도 아니라 **이 폰트 표의 색인**을 쓴다(세션1 §3.11의
"자체 문자 코드" 추정이 확정됐다). 확인된 값:

`あ`=0x026, `れ`=0x070, `ィ`=0x078, `ス`=0x08E, `ナ`=0x09F,
`フ`=0x0AA, `！`=0x0CD, `ー`=0x0CF, `？`=0x0D7

시트(`work/font_full_0.png`) 순서는 숫자 → 영문 → 히라가나 → 가타카나 →
기호 → 한자다. **코드 폭(1바이트/2바이트)과 제어코드는 미확정** — 다음 과제.

## 5.6 한글화 관점의 예산

- 전각 슬롯 **1,504개** = 글리프 공급의 천장(재배치 없이)
- 레코드가 **가변 길이 + 오프셋표**이므로, 표를 다시 쓰면 **글리프를 늘리거나
  줄일 수 있다** — 제자리 고정 길이 제약이 없다
- 파일 안 `0xA681`~`0xAA02`(약 872 B)가 0 패딩이라 소폭 여유가 있고,
  그보다 **XOR 델타 재인코딩으로 확보되는 여유가 훨씬 크다**
- 한글 글리프는 16×16이 아니라 좌·우 8px 열 두 개로 나뉘어 인코딩되므로,
  인코더는 열마다 독립 XOR 체인을 만들어야 한다

# 6. 폰트 인코더 (세션 2, 완료)

`tools/font_codec.py`(디코더+인코더, 단일 출처) / `font_roundtrip.py`(전수 검증) /
`font_build.py`(재빌드·예산).

- 인코딩 = 최소 인코딩. 바이트 0·16에서 누산기 리셋, `raw[i] != acc` 일 때만
  플래그를 세우고 `raw[i]^acc` 를 델타로 낸다.
- 원본 배치 정책(실측) = **공유 없음 · 빈틈 없음 · 정렬 없음**.

| 검사 | 결과 |
|------|------|
| 레코드 왕복 `encode(decode(r))==r` | 전각 **1504/1504**, 반각 **128/128** |
| 구간 전체 재구성 == 원본 | 전각 40,065 B / 반각 2,118 B **바이트 동일** |
| 무교체 재빌드 == 원본 파일 | **바이트 동일** |
| 글리프 교체 후 재디코드 | 통과 |

**바이트 예산**: 전각 데이터 상한 `+0xAA03` → 37,955 B(표 3,008 제외), 현재 37,057 B.
빈 글리프 = 4 B이므로 **안 쓰는 한자를 비우면 슬롯당 약 21 B 회수**된다.
→ 병목은 바이트가 아니라 **슬롯 1,504개**.

한글은 나눔명조 **14px**만 16×16 상자에 맞는다(15·16px은 11,172자 중 5,900~7,800자 넘침).
평균 인코딩 크기 24.2 B(임계값 128) ~ 26.1 B(Bold/96). 원본 일본어 평균은 24.8 B.

# 7. ★ 대사 스크립트 포맷 (세션 2, 확정)

## 7.1 저장 위치

대사는 `/FIELD/*.MDT`(36개) 안의 **이벤트 스크립트 섹션**에 인라인으로 있다.
MDT 헤더 = `[타입8|오프셋24][크기32]` × 64 섹션표. 파일이 **그대로 적재**된다
(E800.MDT → 버스 `0x00280000`, 파일 오프셋 == RAM 오프셋 − 0x80000).

`E800.MDT`의 스크립트 = 레코드 12, `+0x1348 ~ +0x30A8` (7,520 B).
런타임 변수 `*(0x06021D2C)` = `0x00281348` 로 현재 스크립트를 가리킨다.

## 7.2 문자 인코딩 (확정)

스크립트는 **BE16 워드 스트림**이고, 메시지 블록 안에서만 바이트 단위로 읽는다.

| 바이트 | 의미 |
|--------|------|
| `0x20`~`0xFF` | **1바이트 글자** — 폰트 코드 = 바이트 − 0x20 (코드 `0x000`~`0x0DF`) |
| `0x10`~`0x14` | **2바이트 이스케이프** — 폰트 코드 = `0xE0 + (b−0x10)*256 + 다음바이트` |
| `0x00`~`0x0F`, `0x15`~`0x1F` | 제어코드 |

전각 슬롯 수와 정확히 맞아떨어진다: **1,504 = 224 + 5 × 256**.

검증: 이 규칙으로 전 메시지를 렌더하니 한자가 정상으로 읽힌다 —
「オレにも分かんないよ！ 突然 目の前が暗くなって‥」
「ジャスティン フィーナ それに スー！ みなさんは 冒険を ご希望ですね？」
「ついに 展示アイテムが そろいましたね さあ 地上への扉を開けましょう」

실측 코드: `あ`=0x026, `れ`=0x070, `ィ`=0x078, `ス`=0x08E, `ナ`=0x09F,
`フ`=0x0AA, `！`=0x0CD, `ー`=0x0CF, `？`=0x0D7.

## 7.3 메시지 블록과 분기 (확정)

```
20 LL  <LL바이트>            메시지 블록. 블록은 0F… 로 시작해 07 로 끝난다. LL은 짝수.
1000 30LL                    조건부 **상대** 스킵 — 이후 LL바이트를 건너뛴다
```

**절대 오프셋 점프는 없다.** `1000 30LL`의 스킵 대상이 알려진 오피코드일 확률
**99.0%**(무작위 기준선 24.2%). 따라서 텍스트 길이를 바꿔도 절대 오프셋
재계산은 필요 없고, **`20 LL` 과 그 메시지를 감싸는 모든 `1000 30LL` 만 갱신**하면 된다.

⚠️ **둘 다 1바이트라 상한 255다.** 이게 진짜 예산이다.

그 밖의 자주 쓰이는 오피코드: `7000 80XX YYYY`(3워드), `1001 40XX YYYY`(3워드),
`5000/5001 XXXX`(2워드), `F000`(1워드). `0x07xx`·`0x40xx` 인수는 플래그/변수 ID이며
홀수 값이 섞여 있어 **오프셋이 아니다**.

## 7.4 모집단·예산 실측 (36개 MDT 전수)

- 메시지 블록 **282개**, 글자 **16,135자**
  (1바이트 14,106자 + 2바이트 2,029자) → **평균 1.13 B/글자**

## 8.4 ★ 남은 문제 — 제어코드 인수 길이 (다음 과제)

추출문에 소수의 오파싱이 있다. 원인은 **제어코드의 인수 바이트를 글자로 읽는 것**이다.

예: `0A 0C 00 10 46` 은 제어 `0A 0C 00` + 인수 `0x10` + 글자 `0x46`(=`あ`)인데,
인수 `0x10`을 2바이트 이스케이프로 오인해 `0x126`이라는 **유령 코드**를 만들어냈다
(「あんまり」가 「〈126〉んまり」로 나왔다).

→ **제어코드별 인수 길이표를 확정해야 추출이 완전해진다.**
관측된 형태: `0F xx`(2B), `0E 00 xx`(3B), `0A 0C 00 xx`(4B), `09 0C 00 xx`(4B),
`0B 00 xx …`, 단독 `01`(개행)·`02`(페이지)·`06`·`07`(종료)·`09`.
검증 방법이 이미 있다: 파싱이 **정확히 `LL`바이트를 소비하고 `07`에서 끝나야** 한다.

# 9. 제어코드 문법 (세션 2, 실용 수준 확정)

`tools/script_parse.py` — 메시지 블록을 **텍스트 런 ↔ 제어코드**로 가르는 파서.
`parse()` ↔ `emit()` 이 **282/282 바이트 왕복 일치**한다. 이게 재삽입 안전성의 핵심 불변식이다.

## 9.1 ★ 종결자 처리 (중요한 함정)

**메시지 블록의 마지막 바이트는 항상 `0x07`** (282개 전량 실측).
이걸 고정하지 않으면 `10 07` 을 한자 이스케이프(=`話`)로 오인해 **종결자를 먹는다.**
실제로 그 버그 때문에 대사 끝에 `話`·`炎`·`役` 같은 유령 글자가 붙었다.
→ 본문은 `blk[:-1]` 만 파싱하고, 마지막 바이트는 종결자로 확정한다.

## 9.2 길이표 (실측)

| 길이 | 제어코드 |
|------|----------|
| 1바이트 | `01`(개행) `02`(페이지) `05` `06` `07`(종료) `09` `0B` `1A` |
| 2바이트 | `00` `03` `04` `08` `0A` `0D` `15`~`19` `1B`~`1F` |
| 3바이트 | `0C` `0E` `0F` |

대표 형태: 메시지 머리 = `0F 21 0A` + `0C 00 xx` (6바이트), 화자·연출 = `0F xx yy`,
`0E 00 xx`. `0x10`~`0x14`는 제어가 아니라 **한자 2바이트 이스케이프**다.

## 9.3 확정 방법과 한계 (정직하게)

- **LL 제약만으로는 거의 갈리지 않는다.** "정확히 LL바이트 소비 + 07 종료"를 만족하는
  길이표가 많다. 글자가 대부분 1바이트라 어긋난 파싱도 스스로 되맞춰지기 때문이다.
- **표기 중의성이 있다.** `0F 21 0A 0C 00 11` 은 `0F 21|0A 0C|00 11`(2+2+2) 로도
  `0F 21 0A|0C 00 11`(3+3) 으로도 갈라지며 **텍스트 경계는 같다.**
  우리에게 필요한 건 경계뿐이므로 문제되지 않는다.
- 그래서 **추출문 품질 지표**로 골랐다: 나쁜시작(제어 직후 런이 요음·촉음·장음으로 시작),
  낱글자런(1~2자짜리 런), 유령한자(1회만 등장), 파싱실패.
- 최종 지표: 나쁜시작 **5**, 낱글자런 **64**, 파싱실패 **0** (글자 15,817자 기준).
  남은 낱글자런 ~0.4%는 아직 미확정 구간이다.

⚠️ **미확정 구간이 남아 있다.** 번역 재삽입에서 제어코드를 **불투명하게 그대로 보존**하면
의미를 몰라도 안전하지만, 경계가 틀린 곳에서는 제어 바이트를 글자로 바꿔 쓸 위험이 있다.
→ 재삽입 도구는 **바꾸지 않은 블록이 바이트 단위로 원본과 같은지** 반드시 검사해야 한다.

# 10. 추출기·재삽입 빌더 (세션 2, 완료)

`tools/script_extract.py` → `work/trans/script.tsv`
`tools/script_build.py` → `work/build/*.MDT`

## 10.1 번역 자산 형식

TSV 한 줄 = 메시지 블록 하나. 열 = `file / off / len / ja / ko`.

- `ja` 는 **원문 보호** — 절대 수정하지 않는다. 빌더는 `ko` 만 읽는다.
- 제어코드는 `{hex}` 로 **불투명 보존**, 개행 `\n`(=`01`), 페이지 `\p`(=`02`).
  토큰의 개수·순서를 바꾸면 안 된다.
- `ko` 가 비면 원문을 그대로 둔다.

## 10.2 ★ 재삽입 정책 — 블록 길이 고정 + 공백 패딩

MDT 헤더에는 서로 겹치는 섹션 레코드가 있어(예: E800의 레코드 63은 파일 끝을 넘는다)
**섹션을 밀어 재배치하는 것은 위험하다.** 그래서 기본 정책은

> **각 메시지 블록의 길이를 원본과 정확히 같게 유지하고,
> 남는 자리는 종결자 앞에 공백(`0x20`)으로 채운다.**

줄 끝 공백은 화면에 보이지 않는다. 이러면 섹션 크기가 안 변하므로
`1000 30LL` 스킵도, MDT 헤더도 건드릴 필요가 없다.
(`--allow-resize` 로 완화 가능하나, 그때는 헤더 갱신 책임이 생긴다.)

## 10.3 불변식 (하나라도 어기면 빌드 실패)

1. `ko` 가 빈 메시지는 **원본과 바이트가 완전히 같아야 한다**
2. 블록 길이는 **짝수, ≤ 255**, 그리고 기본 정책에서는 **원본과 동일**
3. 인코딩 불가 문자는 **조용히 건너뛰지 않고 빌드를 실패**시킨다
4. 다시 파싱한 결과가 넣으려던 토큰열과 같아야 한다
5. 같은 글자에 코드가 둘 이상이면(예: `十` = `0x126`·`0x343`)
   **원본에서 실제로 쓰인 코드**를 고른다 — 안 그러면 `ko=ja` 왕복이 깨진다

## 10.4 검증 결과 (통과)

| 검사 | 결과 |
|------|------|
| 번역 없음 → 재빌드 | 36/36 파일 **바이트 동일** |
| `ko = ja`(원문 그대로) → 재빌드 | 282개 전량 재인코딩, 36/36 파일 **바이트 동일** |
| 일부 메시지 단축 → 재빌드 | 블록 길이·섹션 크기 **불변**, 남는 자리 공백 패딩, **섹션 밖 완전 동일** |

## 12.3 빌더 검사 수정

# 13. ★ 스크립트 VM 해석 — §7·§9의 메시지 구조는 틀렸다 (2026-08-04)

실기에서 미번역 대사가 깨져 보이는 것을 사용자가 발견해 재조사했다.
결론: **§7에서 "확정"이라 쓴 `20 LL` 메시지 구조가 틀렸다.**

## 13.1 인터프리터 (실측)

`0x0601E5C4` = 스크립트 인터프리터 본체. 진입 경로는

```
0x0601E4E4  BSR 0x0601E56A      ; ID → 진입점 주소 조회
0x0601E4FC  MOV.L R13,@(8,R14)  ; R14=0x06020018 → *(0x06020020) = 스크립트 실행 포인터
0x0601E2C8  MOV.L @(8,R14),R1   ; 그 포인터를 읽어
0x0601E2CC  BSR 0x0601E5C4      ; 인터프리터 호출
```

- 실행 포인터 변수 = **`0x06021CFC`** (현재 값이 `0x0028146C` = E800.MDT +0x146C, 스크립트 섹션 안)
- `0x0601E56A` = **ID → 진입점** 조회. 테이블은 MDT **섹션 레코드 11**
  (`[BE16 ID][BE16 섹션내 오프셋]` × N, `FFFF FFFF` 로 끝). E800은 22개 진입점.

## 13.2 ★ 명령 형식

```
0601E5E4:  R5 = *(포인터);  포인터 += 2      ; **워드 단위로 전진**
0601E5EC:  R5 = *(u16)R5                     ; BE16 명령 워드
0601E5F2~: R0 = R5 >> 12                     ; **상위 니블 = 오피코드**
```

| 오피코드 | 핸들러 | 뜻 |
|---|---|---|
| 1 | `0x0601E69C` | |
| **2** | `0x0601E700` | **텍스트 출력** |
| 4 | `0x0601E88E` | |
| 5 | `0x0601E9F2` | |
| 6 | `0x0601EA4A` | |
| 7 | `0x0601EAD6` | |
| **8** | 인라인 | **상대 점프** (다음 워드를 포인터에 더함) |
| 9 | `0x0601EFA0` | |
| **F** | 인라인 | **종료** |

## 13.3 ★★ 내가 틀린 지점

텍스트 핸들러 `0x0601E700` 은 명령 워드를 **`0x0FFF` 로 마스크**한다(`0x0601E71E`).

> **텍스트 길이는 12비트다.** 명령은 `0x2NNN`, NNN = 길이.

세션2 §7에서 이걸 **`20 LL`(상위 바이트가 0x20, 8비트 길이)** 로 읽었다. 그 결과

- 길이가 `0x100` 이상인 메시지(`0x212E` = 302 B 등)를 **전부 놓쳤다**
- 놓친 것을 메우려고 "블록은 `0x07` 로 끝난다", "홀수면 패딩 1바이트" 같은
  **규칙을 덧붙였는데 그것도 관측에 끼워맞춘 것이었다**

그리고 §9의 "제어코드 길이표"도 같은 뿌리에서 나온 추측이다. 워드 스트림이므로
바이트 단위 길이표라는 전제 자체가 성립하지 않는다.

## 13.4 검증이 이걸 못 잡은 이유 (교훈)

`verify_build` 는 **추출된 282개가 의도대로 들어갔는지**만 봤다.
"추출이 완전한가"는 검사하지 않았으므로 282/282 통과가 나왔고,
누락은 실기 화면에서야 드러났다.

→ **재삽입 검증과 별개로 「추출 완전성」 검증이 반드시 있어야 한다.**
`tools/verify_extract.py` 가 그 역할(메시지 밖에 일본어가 남으면 실패)이며,
이 도구를 처음부터 돌렸다면 세션 초반에 잡혔을 문제다.

# 14. 런 단위 제자리 교체로 전환 (2026-08-04)

§13에서 VM 구조를 확정했지만 **워크 도달률이 10.7%**에 그쳤다.
텍스트 출력 후 인터프리터가 리턴(입력 대기)하고 이후는 맵 이벤트 등 다른 경로로
재진입하기 때문에, 진입점 테이블만으로는 스크립트 전체에 닿지 못한다.
진입점 탐지를 일반화해 2000.MDT 진입점을 22→98개로 늘려도 도달률은 그대로였다.

그래서 **메시지 구조를 아예 쓰지 않는 방식**으로 전환한다.

## 14.1 방식

스크립트 섹션에서 **연속된 글자 코드**를 런으로 잡고, 런을 **같은 바이트 길이로
제자리 교체**한다. 길이를 안 바꾸므로 명령 스트림·메시지 길이·조건부 스킵·점프가
전부 그대로다. **구조를 몰라도 안전하고, 누락이 원리적으로 없다.**

`tools/extract_runs.py`

## 14.2 노이즈 판별 (실측)

스크립트 섹션에는 3D 데이터·명령 인수가 우연히 가나로 읽히는 런이 대량으로 섞인다.
길이·가나비율로는 안 갈린다. 확실한 대사 7런 vs 확실한 노이즈 20런을 재보면

| 지표 | 대사 | 노이즈 |
|---|---|---|
| **라틴 알파벳 비율** | **0.000** | **0.143** |
| 공백/글자 | 0.054 | 0.007 |

→ **라틴 알파벳 비율 8% 초과면 노이즈**로 판정한다.

# 16. ★★ 블록 내부 디코더 확정 — 중의성 해소 (2026-08-05)

§7·§9·§12에서 「제어코드 길이표」와 「`0x10~0x14` 중의성」으로 남아 있던 문제를
**인터프리터에서 직접 읽어 종결**했다. 추측·통계 없음.

## 16.1 찾아간 경로 (기록)

메모에 「블록 내부 파서 = `0x0601C93C`」라고 적혀 있었으나 **틀렸다** —
`0x0601C93C`는 표 `0x0601FFBC`에서 창 프리셋을 골라 좌표·크기 4개를 돌려주는
**텍스트창 설정 루틴**이다(R4=프리셋 번호). 실제 경로는 이렇다.

```
0x0601E700  op2 핸들러 — 길이 &0x0FFF, 창 설정, 메시지 구조체에 텍스트 포인터 저장
0x06020034  메시지 구조체.  +0x14 = 텍스트 포인터
0x0601D0D2  포인터를 VM 포인터 변수 0x06021CFC 에 넣고 → BSR 0x0601D4AA → 회수
0x0601D4AA  ★글자 루프.  0x0601D4E2 에서 CMP/GE #0x10 으로 글자/제어 판정
0x0601D5A4  ★★바이트 디코더 (아래)
0x0601DBFE  글리프 진입점 — 첫 명령이 ADD #0xE0,R5 = **코드 − 0x20**
```

## 16.2 ★ 디코더 (기계어 그대로)

```
p = *(0x06021CFC);  b = *p++;  tok = b
if b >= 0x0A:
    if   b < 0x10:   인수 = (*p++ << 8) | *p++      # 제어코드 + 2바이트 인수
    elif b < 0x20:   tok  = ((b - 0x0F) << 8) | *p++ # 2바이트 글자
    else:            pass                            # 1바이트 글자
*(0x06021CFC) = p
호출부: tok >= 0x10 → 글자(글리프 = tok − 0x20) / tok < 0x10 → 제어코드
```

| 바이트 | 뜻 | 총 길이 |
|--------|-----|--------|
| `0x00`~`0x09` | 제어코드 (인수 없음) | **1 B** |
| `0x0A`~`0x0F` | 제어코드 + **2바이트 인수** | **3 B** |
| `0x10`~`0x1F` | **2바이트 글자 선두** — 글리프 = `0xE0 + (b−0x10)*256 + 다음바이트` | 2 B |
| `0x20`~`0xFF` | 1바이트 글자 — 글리프 = `b − 0x20` | 1 B |

★ **`0x10~0x14`는 제어코드가 아니다.** 디코더는 `b >= 0x10`을 무조건 글자로 본다.
   중의성은 **존재하지 않았다** — §9·§12의 중의성은 내 잘못된 길이표가 만든 허상이다.

★ 선두 상한이 `0x1F`인데 실제로는 `0x14`까지만 쓸 수 있다:
  글리프 슬롯이 정확히 **1,504 = 0xE0 + 5×256**이라 `0x15` 이상은 표 밖으로 나간다.
  **폰트 표 크기가 선두 범위와 정확히 맞아떨어지는 것**이 이 해석의 독립 확증이다.

# 17. 세션4 — 블록 앵커링으로 인수 침범 0건, 재빌드 (2026-08-05)

§16의 확정 디코더를 `extract_runs.py`에 실제로 반영하고 전체 파이프라인을 다시 돌렸다.

## 17.1 1차 수정 — 바이트 규칙만 교체 (부분 개선)

`0x0A~0x0F`를 만나면 인수 2바이트까지 통째로 건너뛰도록 고치자(바이그램 추측
`lead10_is_ctrl`·수동 보정표 `junk_prefix.tsv` 제거), 같은 기준(§16.4 방식) 실측으로
**인수 침범이 137건 → 64건**으로 줄었다. 그러나 0은 아니었다.

## 17.2 ★ 잔차 원인 — 블록 진입 전 위상 오염

잔차 사례(2000.MDT 섹션 +0xEB2E)를 직접 추적: 진짜 블록은
`0A 00C0 | パームの港 | 0A 00D0 | へ | 07`로 시작하는데, **블록 시작 바로 앞 바이트**
(+0xEB2D)가 우연히 `0x0E`(제어+인수 패턴)라서 스캐너가 블록 헤더 `0A`를 그 인수로
삼켜버리고, 인수 하위바이트 `C0`를 다음 런의 첫 글자로 오독해 「ニパームの港」가 나왔다.
**맹목적 전체 스캔은 블록 밖(VM 명령·3D 데이터)에서 우연히 일치하는 패턴에 취약**하다
— 규칙 자체는 맞아도 진입 위상이 틀리면 소용없다.

## 17.3 해법 — 검증된 블록을 앵커로

`text_vm.scan_candidates`(워드 정렬 `2LLL` 헤더) + `decode_block`으로 **완전히
검증되는 블록만**(끝까지 정렬·글리프 유효·`07` 종단·일본어 비율 0.8↑·4자 이상)
신뢰하고, 그 바이트 범위를 맹목 스캔에서 통째로 제외한다. 검증된 블록 안의 글자런은
`decode_block` 결과에서 직접 뽑으므로 **인수를 원리적으로 포함할 수 없다.** 나머지
구간(검증 못한 부분)은 기존 맹목 스캔이 보완한다. 도구 = `extract_runs.trusted_blocks`
/ `trusted_runs`, 저수준 스캔 후보는 `text_vm.scan_candidates`(신규).

## 17.4 검산 (같은 기준, 3단 비교)

검증된 블록의 제어코드 인수 위치를 기준으로, 번역 대상 런(translatable+not noise)이
그 위치를 포함하는지 셌다:

| 스캐너 | 런 | 글자 | 인수 침범 |
|---|---|---|---|
| 옛(세션3, 바이그램 추측) | 5,905 | 68,253 | **137건 (2.32%)** |
| 1차 수정(규칙만 교체) | 5,369 | 68,241 | 64건 (1.19%) |

# 18. §15.4 잔존 미번역 구간 전수 계산 — 노이즈 파일 발견 (2026-08-05)

## 18.1 실기 제보 — 「안다!」의 정체

사용자가 실기에서 `안다! 그럼 코스를 설명해 드리겠습니다`를 보고 「안다!」가
어색하다고 제보했다. 추적해 보니 `E800.MDT +0x3E1`(`はい！`, 3바이트)가
**미번역 상태**(`ko=''`)였다 — 화면의 「안다!」는 번역문이 아니라, 원문 코드가
이미 한글로 재배정된 폰트 슬롯을 참조해서 생긴 §15.4 버그의 **실물 증거**다.
`네엣!`(4B)은 예산 3B를 넘어 `넵!`(3B, 예산과 정확히 일치, 느낌표 포함)으로 반영.

## 18.2 1차 계산 — 노이즈 오염 발견

`census_untranslated_codes.py`로 처음 돌리자 **미번역 20,049자 / 충돌 코드 416종**
(한글 배정 827종의 절반!)이 나왔다. 그런데 상위권(`0004.MDT` 8,892자)의 실제 텍스트를
찍어보니 `自自自ヅまッぼ`, `べらさヴくLゼゥクー5ャ…` 처럼 **명백한 노이즈**였다.

## 18.3 원인 — 대사 자체가 없는 파일

`trusted_blocks`(§16 확정 디코더로 완전 검증되는 블록)를 **파일의 모든 섹션**에
걸어 보니, `0000·0004·EC08.MDT`는 신뢰 블록이 **0개**였다. `E8FF.MDT`는 1개
나왔으나 내용이 `るNきXガ…`로 **라틴 문자가 섞여** 있어(진짜 일본어 대사에는
안 나옴) 가짜였다. 즉 **이 4개 파일은 애초에 대사 스크립트가 아니다** —
`script_section()`이 실제 대사 블록이 하나도 없는 상황에서 어쩔 수 없이
가장 앞 섹션을 fallback으로 고른 것이고, 거기서 맹목 스캔이 3D 데이터를
가나로 잘못 읽은 게 906개 런(글자 상당수)이었다.

# 19. 세션6 (2026-08-05) — 「射レント博물관」의 진짜 원인 규명

## 19.1 계기 — 실기 스크린샷

세션5까지 추출에 ` 射レント博物館・ホール`, ` 歓ーザ遺跡`, ` 殺だ基地` 같은
**깨진 접두**가 20건 있었고, 「깨진 글자는 버리고 뒤만 번역」으로 대응해 왔다.
사용자가 실기 스크린샷(`アレント博物館・図書室へ`가 화면에 멀쩡히 표시)을
제시하면서 **추출이 틀렸다**가 확정됐다. 화면에 정상 표시되는데 추출이 깨져
있으면 100% 추출 잘못이다.

## 19.2 원인 사슬 (전부 바이트로 확인)

```
01C68  20 10 | 97 e1 e6 bd 14 5b 10 88 10 52 ea d0 ef e0 | 07 00
       └헤더┘  └─ アレント博物館・ホール ──────────────┘  └종단+패딩
```

1. `trusted_blocks()` 종단검사가 `toks[-1].code == 0x07`(**마지막** 토큰이 07)을
   요구했다. 그런데 블록 길이는 **워드 정렬**이라 본문+`07` 이 홀수면 뒤에 패딩
   `00` 이 하나 붙는다 → 마지막 토큰이 `00` → **진짜 대사 블록 376개가 탈락**.
2. 탈락한 블록은 **맹목 스캔**이 담당하는데, 얘는 블록 시작을 모르니 **헤더
   `20 1X` 부터** 읽어 `20`=스페이스, `10 97`=2바이트 글자로 오독하고 **첫 글자
   `ア` 의 바이트 `97` 을 인수로 먹었다** → ` 射レント博物館`.
3. 런이 헤더 2바이트를 포함하니 **빌더가 헤더 위에 번역문을 썼다** → 실측 **8건**
   에서 헤더 `20 10` → `a7 10` 파괴(나머지 12건은 아직 번역이 없어서 무사했을 뿐).

★ `scan_candidates` 는 처음부터 정답을 알고 있었다:
`01C6A L=16 endOK glyphOK jp1.00 'アレント博物館・ホール'`.

## 19.3 수정 3종 (`extract_runs.py`)

1. **종단검사 완화** — ctrl `0x07` 을 뒤에서 찾고 **그 뒤가 전부 ctrl `0x00` 패딩**
   이면 통과.
2. **헤더 차단** — 맹목 스캔 차단 범위를 `[off, off+L)` → `[off-2, off+L)` 로.
   본문만 막으면 앞쪽 런이 다음 블록 헤더를 삼킨다(실측 2000.MDT +0x0C49C).
3. **주소 순서 채택** — 겹치는 후보를 「긴 것부터」가 아니라 **주소 순서**로 고른다.
   실측: 진짜 블록 `0C492`(헤더 `20 62`, LLL=98)를, 그 본문 한가운데 ` た`(`20 63`)
   를 헤더로 오인한 가짜 `0C4AC`(LLL=99)가 **1바이트 더 길다는 이유로** 이겨서
   `こんなに たくさん` 이 `こんなに`/`くさん` 으로 찢어졌었다. 진짜 블록은
   순차·비중첩 배치라 왼쪽부터 훑으면 복원된다.

## 21.6 37개 중복 파일 전파 완료 (같은 세션 후속, `tools/propagate_ui_dup.py`)

§20.9 방식(오프셋 산술 아닌 **원문 바이트열 직접 검색**)을 정식 도구로 재작성.

  → **바이트 직접 검색만 신뢰**.
- 방법: FIELD/BATLE TEXT2.BIN 에 실제 적용한 (원문바이트, 번역) 쌍 1,308개를 뽑아

  `0x00`(이전 레코드 종단, 또는 파일 시작)** 인 경우만 진짜 매치로 인정, 그 슬롯에

## 21.9 ★★★ 진짜 근본원인 — 널 패딩이 문자열 **순번**을 밀었다 (2026-08-07)

§21.8 반영 후 실기: 메뉴 라벨이 **빈칸**. 사용자 제보 "군데군데 보이고 안 보이고 랜덤".

### 내가 세운 첫 가설은 틀렸다 (기록)
"이 렌더러는 2바이트 토큰만 받는다"(원본 `道具`=`10 1a 10 1b` 2바이트 vs 내
`도구`=`58 5e` 1바이트). 마침 `変更`→`변경`, `交換`→`교환` 두 개만 순수 2바이트라
**공짜 대조군**이 디스크에 있었고, 사용자 확인 결과 **`변경`은 나오고 `교환`은 안 나왔다**
→ 가설 반증. **가설을 세우면 그걸 반증할 대조군부터 찾을 것.**

### 진짜 원인
`FIELD_CMDMN.BIN` 0x160F8 에 **16비트 문자열 인덱스표**가 있다:

    00 00  00 01  00 02  00 03  00 04  00 38  00 06 … FF FF

렌더러는 기준 `0x060C8060`(=file 0x16060)부터 **널을 세며 N번째 문자열**을 찾는다.
번역이 짧아 남는 자리를 **`0x00` 으로 패딩**했더니 **빈 문자열이 하나씩 끼어들어
그 뒤 순번이 전부 밀렸다** → 어떤 건 나오고 어떤 건 빈칸/엉뚱한 문자열.

★**되읽기 검증으로는 절대 안 잡힌다** — 내가 쓴 바이트와 읽은 바이트는 같으니까.

### 수정
패딩을 **공백 `0x20`**(글리프 코드 0x00 = 공백)으로 바꿨다. 원본도 `使う `·`変更 `
처럼 트레일링 공백을 쓰므로 자연스럽다. 고친 곳 5군데:
`bintext.rebuild` / `ui_build` / `propagate_ui_dup` / `verify_ui_dup` / `build_sysmenu`.

**새 회귀 테스트(필수)**: 되읽기만으로 부족하다 → **원본과 빌드의 널 경계(문자열 시작
오프셋 목록)가 완전히 일치하는지** 대조할 것. 실측: CMDMN 23/23, SAVER 25/25,
SHOP 24/24 경계 일치.

전체 재빌드(TEXT2 2개 + 37중복 + 시스템메뉴 4개) 후 ISO: 75파일, ECC 11,505섹터,
되읽기 75/75, `work/gdm_kr.xdelta` **180,524 B**.

## 21.10 반각 혼재 문자열 + 렌더 폭 잔상 (2026-08-07, §21.9 후속)

§21.9(공백 패딩) 반영 후 실기: `마법・기술` 정상 렌더 ✅. 그런데 두 가지가 남았다.

### (1) 반각이 섞인 문자열을 통째로 건너뛰었다
`0x03`=반각 전환, `0x04`=전각 복귀. 1차 추출기가 이런 문자열을 "노이즈"로 보고
제외했는데, **전각 구간만 미번역이라 그 부분이 한글 글리프로 깨진다**:
`魔法\x03LV1`→`홀 설LV1`, `本体\x03RAM`→`직편RAM`,
`\x03…RAM\x04が接続されていません`, `\x03…\x04がありません`.
→ `tools/sysmenu2.py` = **세그먼트 인식**(전각런만 번역, 반각·제어는 바이트 보존).
신규 8건 추가 반영(총 72 → **80건**).

### (2) ★렌더 폭 초과 = 잔상
게임은 라벨 자리를 **원본 폭만큼만** 지운다. `魔法・技`(4칸)를 `마법・기술`(5칸)로
번역했더니 **5번째 칸 `술`이 안 지워져 다음 화면을 오염**시켰다(실기 제보).
→ `마법기술`(4칸)로 축약. 같은 이유로 `データ無し`→`데이터없음`(5칸),
`下取りできません`→`되팔 수 없음`으로 조정.
**규칙: 번역의 잉크 칸수 ≤ 원본이 그 자리에 그리던 총 칸수.** 필드 메뉴 탭 그룹
(CMDMN 0x16060~0x160A5)은 그룹 최대폭 4칸(`魔法・技`)까지 허용.

### 패딩 안전성 확인
공백 글리프 = 코드 `0x00`, **한글에 재배정되지 않았고 픽셀 0** — 패딩이 화면에
아무것도 안 그리며 오히려 그 칸을 지운다(잔상 방지에 유리). 확인 완료.

### 빌드

## 21.11 ★반각 폰트 전수 해독 + 반각 메뉴 라벨 한글화 (2026-08-07)

실기 제보: 세이브/로드·메뉴 본문은 정상인데 **가타카나가 그대로**
(`ロード` `セーブ` `カートリッジRAM` `ステータス` `スキル`).
이건 §20.2 에서 "반각은 안 깨지니 필수 아님"으로 미뤄둔 **반각 코퍼스**다.

### 반각표 완전 해독 (`tools/halfwidth.py`)
기존 `work/trans/halfwidth_map.json` 은 개수-대응 다수결로 유도한 **70항목짜리

**규칙은 전각과 동일: 바이트 `b` → 글리프 인덱스 `b − 0x20`.**
  · 인덱스 0x00~0x5F = ASCII 0x20~0x7F
  · 인덱스 0x60~0xC0 = 가타카나·기호(ァ…★)

검증: `カートリッジRAM` = `8a d5 a7 c9 a2 97 52 41 4d`
      → 6A B5 87 A9 82 77 32 21 2D → `カートリッジRAM` ✓

### 한글화 방식
반각 구간을 통째로 **전각 한글**로 교체한다. 문자열 선두는 기본이 전각 모드라
`0x03`(반각 전환)을 빼고 바로 한글을 쓰면 된다. 패딩은 공백(0x20).

| 위치 | 원문 | 한글 |
|---|---|---|
| CMDMN 0x16072 / 0x16077 | `スキル` / `ステータス` | 스킬 / 상태 |
| SAVER 0x0F98C·0x0F991 (SVLD 동일) | `ロード` / `セーブ` | 로드 / 저장 |
| SAVER 0x0F9A1·0x0F9AC (SVLD 동일) | `カートリッジRAM` | 카트리지 |

### 범위 결정 (사용자 지시)
**아이템·장비·캐릭터명은 번역하지 않는다.** 반각 작업은 **메뉴 라벨만** 대상.
`ゴールド` 는 전각·반각 어느 인코딩으로도 디스크에 없어 **그래픽으로 판단**(제외).

### ★★후속 수정 — `0x04`(전각 복귀) 명시 필수
1차 반영 후 실기: `로드`가 **`cr`** 로 나왔다. `0x03` 만 빼고 한글을 쓰면 되는 줄
알았는데, **렌더러가 그 자리에 올 때 이미 반각 모드**라 1바이트 한글 코드
(`로`=0x43→바이트 0x63, `드`=0x52→0x72)가 **반각 글리프 `c`,`r`** 로 읽혔다.
같은 화면의 `본체RAM` 은 `本体` 가 **2바이트 토큰이라 모드와 무관**해 멀쩡했고,
그래서 "어떤 건 되고 어떤 건 안 되는" 것처럼 보여 진단이 헷갈렸다.
→ 교체 바이트 맨 앞에 **`\x04` 를 항상 붙인다**(이미 전각이어도 무해).
실측: `03 cc d5 a8`(ロード) → `04 63 72 20`.

ISO: 75파일, ECC 11,505섹터, 되읽기 75/75, `work/gdm_kr.xdelta` **180,567 B**.

## 22.10 GM3.STZ 조사 결과 (2026-08-08) — **텍스트는 여기에 없다**

`GM3.IDX`(BE16 A + BE16 섹터오프셋 ×1024, 유효 369)로 나눈 369청크를 전수 분류:

| 종류 | 개수 | 헤더 |
|---|---|---|
| `ST5\0` | **245** | 48바이트. `+04`=0001 0030(버전/헤더크기) `+0C`=페이로드크기 `+10`=엔트리수 `+14`=08200000(고정) `+18`=00002000(고정) `+28`=00770000(고정). **페이로드는 0x800(섹터경계)부터** |
| `80 xx xx xx` | **124** | `+04`=03120402 `+08`=**00005622**(=22050, 샘플레이트) `+10`=01F40300. 전부 고정 |

**둘 다 스트림 미디어다.** 근거:
* `80` 계열에 **22050Hz** 고정 필드 → 음성
* ST5 페이로드는 바이트 히스토그램이 0,1,2,3…에 몰리고(0이 10~19%) 청크11은
  `01 00 01 00 …` 반복으로 시작 — LZ 압축이 아니라 **델타 부호화 스트림**
* 245 ≈ 명장면 개수와 비슷하지만 청크 안에 제목 텍스트가 없다

### 텍스트 부재 검증 (전수)

1. 248MB 전체에서 `軍事` `列車` `幽霊船` `機関室` `パームの街` 바이트 검색 → **0건**
2. ST5 245청크 앞 8KB 를 디코드해 «연속 일본어 4자 이상» → 191청크가 걸렸으나
   전부 `ぞ偶緑属化` 류 **우연 일치**(미디어 데이터)
3. 「2바이트글자 + `・`(0xEA) + 2바이트글자」 지문으로 248MB 스캔 → 40건 전부 우연

### ★코드표는 맞다 (검산 완료)

위 결과가 「내 코드표가 틀려서 못 찾는 것」일까 봐 FDATA 글리프를 직접 렌더해 대조:
`軍`=0x144 `事`=0x15F `列`=0x5C3 `車`=0x460 `機`=0x3B3 `関`=0x3AC `室`=0x13E —
전부 해당 한자 모양이 나온다(렌더러가 행/열을 바꿔 그려 90° 돌아 보일 뿐).
**따라서 명장면 목록 텍스트는 디스크 어디에도 평문으로 없다.**

## 22.12 ★스프라이트 출처 확정 — `/FIELD/FACE.DAT` (2026-08-08)

사용자가 준 «화면 진입 전 A / 후 B» 스테이트 2개로 정적 추적을 끝냈다.

1. **B 에만 텍스처 존재** — VDP1 VRAM `0x00A8A2` (A 엔 없음)
2. A→B 새로 올라온 VDP1 VRAM 구간 19개 중 `0x00A29E~0x00B0FE`(3,680B, 고유값 3)
   안에 위치. 렌더하니 `美術設定1` 글자 확인
3. ★★**폰트 렌더가 아니라 «미리 구운 그림»으로 확정** — 게임 Work RAM 에는
   **내 한글 `미술설정` 이 들어 있는데**(swap16 0x4AA95C·0x4AA966·0x4B7984·0x4B7A2C)
   화면 픽셀은 일본어다. 텍스트 경로는 정상 동작 중이고 스프라이트만 별개다.
4. **Mednafen CD 읽기 버퍼**(`Buffers->Data`, 470,400B)를 디스크 이미지와 **바이트
   매칭해 LBA 복원** → 12건 중 **10건이 `/FIELD/FACE.DAT`**(LBA 36038, 4,325,376B) 안.
   나머지 2건은 `/FIELD/SYS_R.STB`.

> **출처 = `/FIELD/FACE.DAT`.** 4.3MB 짜리라 「얼굴 그래픽」으로만 보고 지나쳤던 파일에
> **UI 스프라이트 시트**가 같이 들어 있다.

### 기법 메모 — CD 버퍼 → LBA → 파일

스테이트의 `Buffers->Data` 에서 2048 정렬 위치마다 64바이트를 떠서 디스크 이미지
(raw 2352)에서 `find` 하면 그 오프셋 ÷ 2352 = LBA. 파일표로 되돌리면 파일이 나온다.
**압축 소스라 텍스처 자체는 못 찾아도 «어느 파일이 방금 읽혔는지»는 이걸로 잡힌다.**

### 아직 못 잡은 것 — `終了しますか？` 상자

* A/B 스테이트는 **아이템 화면**이라 그 대화상자가 없다(0x4CA2·0x64A2 는 빈 프레임).
* 먼저 받은 `예아니오.state` 는 디버거 창이 말한 `0x412C0` 과 **다른 순간**에 떠서
  그 자리에 상자가 없다(고유값 172, 렌더하면 무관한 그림).
* → **대화상자가 화면에 떠 있는 순간의 스테이트**가 하나 필요하다.

### 정정 — GM3.STZ 는 무관하다

§22.10 대로 GM3 는 영상·음성 스트림이다. 「GM3 를 깨야 이 스프라이트가 나온다」는
내 판단은 **틀렸다**. 스프라이트는 `FACE.DAT` 에 있다.

  `GM3.STZ`/`MDAT2`)를 뒤늦게 전수 검색 → 텍스처 지문 **전부 0건**.

★**CD 읽기 버퍼는 «마지막에 읽은» 데이터라 이전 화면(표정집 = 초상화 로드) 의
  잔재일 수 있다.** LBA→파일 기법 자체는 유효하지만, **그 순간 화면과 인과관계가
  있다는 보장은 없다.** 「방금 읽힌 파일」과 「이 스프라이트의 출처」를 동일시한 것이
  논리 비약이었다.

### 지금까지 확실한 것만

| 항목 | 상태 |
|---|---|
| 스프라이트 실체 | **미리 구운 그림** — 게임 RAM 엔 한글 `미술설정` 이 있는데 픽셀은 일본어 |
| VDP1 정보 | `美術設定1` 144×16 8bpp 2색 / `終了しますか？` 128×48 8bpp 46색 |
| 디스크 평문 | **전 파일(351개, 크기 무관) × 8bpp·1bpp·4bpp·타일 = 0건** → 압축 확정 |
| 출처 파일 | **미확정** |
| GM3.STZ | 무관(영상·음성 스트림) |

### 다음 세션이 해야 할 것

정적 검색은 완전히 소진됐다. 남은 길은 **동적 분석 하나뿐**이다.

1. **VDP1 VRAM 쓰기 브레이크포인트**(`美術設定1` 은 그 실행의 텍스처 주소, 예: 0x00A8A2)
   → 멈춘 PC 와 **전송원 주소**를 얻는다. 소스가 Work RAM 이면 그 주소가 곧 전개
   버퍼이고, 거기서 역으로 적재 루틴·파일을 짚을 수 있다.
2. 브레이크포인트가 없으면 **DMA 레지스터 스냅샷** — 스테이트의 SCU/DMA 레지스터에
   마지막 전송원이 남아 있을 수 있다(미확인, 조사 가치 있음).
3. `.state1` 은 설정자료집 화면이 맞다(프레임버퍼 렌더로 확인). 다만 그 프레임에
   `終了しますか？` 상자는 **아직 안 그려져 있다** — 상자가 떠 있는 순간의 스테이트가
   따로 필요하다.

## 22.14 ★★`parse_state.py` 의 레코드 시작 오프셋이 틀렸다 (2026-08-08)

`美術設定1` 텍스처를 찾을 때 VDP1 VRAM 베이스를 `parse_state.records()` 가 준
`0x007B825` 로 썼는데, **그 자리는 스테이트 레코드 헤더 영역**이었다
(`V[:32]` 이 `dingHIRQ…SeqSeen…` 같은 섹션 이름으로 나온다).

**진짜 베이스를 바이트 패턴으로 다시 잡았다:**

```python
pat = bytes([4]) + b'VRAM'          # [1B 이름길이]["VRAM"][4B LE 크기][데이터]
i   = state.find(pat)
size = struct.unpack_from('<I', state, i+5)[0]
data_start = i + 9
```

| 레코드 | 헤더 | 데이터 시작 | 크기 |
|---|---|---|---|
| VDP1 VRAM | 0x007BDBE | **0x007BDC7** | 524288 |
| VDP2 VRAM | 0x02FCD98 | **0x02FCDA1** | 524288 |

### 검증 — 사용자 디버거 값과 정확히 일치

텍스처 행11 이 절대 `0x00866F7` 에 있으므로
VRAM 오프셋 = `0x866F7 − 0x7BDC7 = 0xA930`, 텍스처 시작 = `0xA930 − 144×11 = 0xA300`.
**사용자 VDP1 디버거가 말한 `Texture address = 0000A300` 과 정확히 같다.**

★즉 §22.11~22.13 에 적은 VRAM **주소**들은 베이스가 틀려 어긋나 있었다.
  (텍스처 «데이터» 자체는 제대로 떠서 렌더까지 맞았으므로 그 부분 결론은 유효하다.)

⚠️ 다른 프로젝트에서도 `parse_state.records()` 를 쓸 때 **데이터 시작 오프셋을
   `[1B len][name][4B size]` 규칙으로 직접 재계산해 검산할 것.**

### 다음 세션 — 여기서 시작하면 된다

베이스가 확정됐으니 VDP1 **커맨드 테이블**을 제대로 읽어 `終了しますか？` 상자를
찾을 수 있다. 커맨드는 32B 단위이고 `CMDSIZE`(+0x0A) 상위6비트 = 폭/8, 하위8비트 = 높이,
`CMDSRCA`(+0x08) × 8 = 텍스처 주소.
* 128×48 → `CMDSIZE == 0x1030`
* 144×16 → `CMDSIZE == 0x1210`

단 VRAM 오프셋 0 이 커맨드 테이블이 아닐 수 있다(2026-08-08 시도에서 128x2 명령이
3000개 나옴 = 잘못된 위치). **커맨드 테이블 선두는 VDP1 레지스터 또는 `Draw End`(0x8000)
로 끝나는 정상 체인을 찾아 확정할 것.**

## 23 ★★그림 압축 해독 — 예/아니오 상자·설정자료집 띠 한글화 완료 (2026-08-08)

### 23.1 「그림이냐 글자냐」 — 논쟁 종결

`終了しますか？` 상자를 두고 세션 내내 「폰트 렌더」↔「그림」을 뒤집었다.
**결정적 증거는 폰트 표에 있었다**: 우리 패치는 다음 슬롯을 전부 한글로 덮었다.

    終(0x23D)→탕  了(0x23E)→탈  し(0x03B)→한
    ま(0x062)→었  す(0x03D)→게  か(0x02F)→나

런타임 폰트 렌더라면 화면에 「**탕탈한었게나?**」가 나와야 한다. 실제로는 완벽한
일본어가 나온다 → **미리 구워 둔 비트맵이 확정**. 픽셀이 FDATA 글리프와 일치한
이유는 개발사가 «원본 폰트로» 구웠기 때문.

★교훈: 「RAM 에 문자열이 없다」보다 **「그 슬롯이 이미 한글인데 일본어가 보인다」**
가 훨씬 강한 증거다. 폰트 슬롯 재활용 패치에서만 쓸 수 있는 반증법.

### 23.2 코덱 — nanash1 공개 소스

동봉 영문패치 README 크레딧의 「Graphics Decompression - nanash1」이 실마리였다.

* https://github.com/nanash1/Grandia_Saturn → `Sprite Compression/`
* 구조: `[BE16 헤더][RLE 데이터][LUT 9B][LUT 인코딩 데이터]`
  헤더 상위2비트=모드(SUB/MOV/XOR), 비트13=「LUT부터 시작」, 하위13비트=표 오프셋
* RLE 은 **0 만** 압축, 나머지 4비트값은 직전값과의 델타를 가변비트로
* README 에 **Digital Museum 디스크 오프셋**이 직접 적혀 있다(유저데이터 기준):
  `0x24634` 전투팝업 / `0xC87248` 전투결과 / `0xCD6B90` 전투휠

이식: `tools/gsprite.py`(해제) `tools/gsprite_comp.py`(압축).
**검증 = 왕복 바이트 일치** — MTOUT 블록을 풀었다 다시 압축해 29,166 B 가
원본과 완전히 같음을 확인. 그리고 「전투 휠」해제 결과가 README 예시
(`표=0x145555566666545460 RLE=6 SUB`)와 정확히 일치.

⚠️`compress.c` 의 `test_next_bits` 는 do-while 이 **「같을 때 계속」**이다.
여기를 뒤집어 옮겼다가 RLE 스트림이 30 KB 로 폭주했다(정상 1.6 KB).

### 23.3 블록 찾는 법 — 표의 유효성으로

바이트 스캔이 아니라 **9바이트 압축표의 조건**으로 찾는다:
18니블 중 앞 17개가 값, 18번째는 0 패딩, 각 값 ≤8, Σ`LUT_SEED[값]`==256.
표 위치 `P` 를 찾으면 `P == off + (head & 0x1FFF) + 2` 로 헤더를 역산.

★처음엔 표마다 `off` 를 8,190회 되짚어서 파일 하나에 9초씩 걸렸다.
**모든 오프셋의 «함의 표위치»를 numpy 로 한 번에 구해** 유효표 집합과
대조하도록 뒤집으니 O(n) 이 됐다 (`tools/find_sprites.py`).

### 23.4 반영 — `FIELD/MTOUT.DAT` 0x13E00

    압축 0x13E00~0x1AFEE (29,166 B) → 해제 51,456 B (0xC900)  MOV RLE=2
      0x2D00  예/아니오 상자 128×48 (「はい」선택)
      0x4500  같은 상자 (「いいえ」선택 — y24~39 만 다름)
      0x5D00 + k*0x900  띠 144×16 ×6  ← 평상시: 획을 0x8F 로 그림
      0x9300 + k*0x900  띠 144×16 ×6  ← 선택시: 0x83 막대에 글자를 0x00(투명)으로 파냄
      검산: 80×16(1280) − 획 425 = 855 = 선택시 0x83 픽셀 수. 정확히 맞는다.

`tools/build_mtout_gfx.py` 로 다시 그렸다. 상자는 글자(0xFF)를 지우고 **같은 행의
나무 픽셀로 인페인팅**한 뒤 한글을 얹었다. 「はい」뒤 빨간 강조(0xBC)는 보존.
숫자 `1·2·3` 은 **원본 글리프를 그대로 떼어 재사용**(목록 글자와 모양 일치).

결과 **27,452 B — 원본보다 1,714 B 작다**. 블록 뒤가 카테고리 문자열표라
여유가 2 B 뿐이었는데 여유롭게 들어갔다.

### 23.5 아직 못 잡은 것 — 몬스터 도감 화면의 같은 상자

같은 그림이 **다른 팔레트 인덱스**로 한 벌 더 있다(설정자료집판과
**완전한 일대일 사상**, 충돌 0/6144: `BC→7C` `C2→02` …). 그래서 바이트 검색으로는
안 잡힌다 → `tools/hunt_gfx.py` 에 **픽셀쌍의 같다/다르다 관계**로 찾는
팔레트 무관 매처를 만들었다(MTOUT 0x2D00 을 재현해 검증).

* 해제본은 스테이트 **WorkRAML +0x5E810 (61,392 B)** 에 있고 VRAM 사본과 완전 일치
* 배제 완료(전부 0건): 350중 220파일 바이트일치 / RAM 상주 22파일 + MDAT2.BIN
  팔레트무관 / CD버퍼가 읽던 `GM3.STZ` 4구간(각 80KB)
* **`MONST.BIN` 은 압축이 아니다** — WorkRAMH `0x2C000` 에 **100% 그대로** 적재
  (235,574/235,656 일치). 내부 포인터 `0x0602C7C0` 이 자기 파일 `0x7C0` 을 가리킨다.
  → 「두 번째 오버레이 코덱」 가설은 **반증됐다**. 엔트로피 7.07 은 안에 든
  압축 그래픽 때문.
* 남은 곳: 안 본 130파일(대부분 `.BBG`) + `GM3.STZ` 나머지

### 23.6 타이틀 화면

「新しく始める」= VRAM `0x6580`, 96×16 8bpp. 원본 폰트로 **정답 마스크**를 만들어

저쪽 문서의 주소가 **우리가 짚은 것과 같다**:

| 역할 | 주소 |
|---|---|
| 디코더(우리가 이미 찾은 진입점) | `0x06015DF0` |

해법 = 이 두 루틴을 손으로 이식하지 않고 **최소 SH-2 인터프리터(`sh2emu.py`)로 실제

`0x800` = EOS, 심볼 = `node >> 3`) + **1바이트 델타 필터**(copy/xor/add) + BE 4바이트 워드
조립 + bias 가산. 청크 종료 시 소스 커서를 **0~4바이트 되감아** 다음 트리-def 와 겹치게
하는 것까지 모델링돼 있다(`decode_end`).

### 바로 쓰려면 필요한 것

`mg_tree.py` 는 **상주 엔진 코드가 든 HWRAM 이미지**를 요구한다(기본 `work/mgame/hwram.bin`).
게임 데이터라 저장소에 없으므로 **우리 세이브스테이트에서 직접 떠야 한다**
